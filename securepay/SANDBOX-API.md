# SecurePay sandbox API boundary

The routes are disabled by default and cannot be enabled with NODE_ENV=production.
No external provider call, money custody or settlement runs in this implementation.

## Sandbox routes
- POST /v1/securepay/tenants/:tenantId/pin/grant — exact body: purpose (enroll or recover), stepUpToken. Optional and disabled unless the recovery authority is configured. Requires a separately validated short-lived, purpose- and tenant-bound step-up JWT with a unique jti. The resulting grant expires in at most two minutes and cannot be used twice.
- POST /v1/securepay/tenants/:tenantId/pin — exact body: pin, purpose (enroll or recover), grantRef.
- POST /v1/securepay/tenants/:tenantId/milestones/:milestoneId/reserve — exact body: pin, expectedAmountCents, idempotencyKey.
- The customer JWT must have the configured issuer, dedicated audience, recent auth_time, configured MFA assurance claim, and valid expiration.
- Responses never include PINs, reusable approval proofs or underlying database errors. A 202 reservation is not a transfer; moneyMoved is false.

## Session recovery
Successful PIN recovery sets a database-backed revocation timestamp and atomically writes a pending notification event. Customer API operations require a verified auth_time strictly newer than this timestamp; the payer identity is locked while checking and using that authentication. Recovery assertions must also be newer. This revokes older sessions at the SecurePay API, not at the external identity provider. The notification outbox stores identifiers and event type only; a restricted sandbox worker is implemented; no contact resolver, real delivery provider or external sends are provisioned. Failed transactions cannot queue a notification or revoke the session.

## Notification delivery boundary
A dedicated worker role can execute only the claim and completion functions, with no direct access to PINs, payment records or the outbox. Notifications use 60-second leases, bounded exponential backoff, eight attempts and dead-letter reconciliation. A stable deployment namespace and event identifier form the provider idempotency key. The configured sink must deduplicate this key even when the first delivery outcome is ambiguous; exactly-once external delivery cannot be guaranteed without that provider contract. Never log event payloads or use an unverified recipient. The worker remains unmounted and no external notification is sent.

## Separate payment authority
The ordinary staff API now mounts a fixed Unix-socket gateway and refuses SecurePay database credentials, PIN pepper, context HMAC or recovery key in its enabled environment. Launch the standalone server/securepay-authority.js with the dedicated credentials and independent customer JWT verifier. Use a separately provisioned, authority-owned socket directory (0700 or 0750), non-world-accessible socket, distinct OS identities and a restricted shared group. The authority validates the original customer token, PIN and database state itself; it never trusts identity headers or requests for arbitrary signing. Gateway failure returns a generic 503 without automatic retry, and its response is allowlisted. The sandbox fixture starts a separate child process; OS-user/container isolation remains unverified. The gateway sees customer PINs and bearer tokens in transit; a compromised gateway could steal them, so this is not an end-to-end defence against full gateway compromise. No provider dispatch or production deployment is enabled.

## Signing-key rotation
After the notification draft apply securepay-key-rotation-draft.sql. Provision separately generated 32-byte context, command and recovery secrets under distinct key IDs in their respective private tables; never export keys to the gateway or payer database login. The standalone authority requires SECUREPAY_COMMAND_KEY in addition to PIN pepper. SECUREPAY_CONTEXT_KEY_ID, SECUREPAY_COMMAND_KEY_ID and SECUREPAY_RECOVERY_KEY_ID select the active signer (default primary). To rotate: insert a new unique key ID, roll out corresponding signer configuration, verify new and old during a bounded overlap, then set the old key active=false; use valid_until for automatic expiry. Never reuse revoked IDs. On compromise revoke immediately, reconcile any in-flight or already committed actions, and fail closed during cutover if necessary. No automatic re-signing or retry. The database checks keys on each signature validation; a command already accepted within an in-flight transaction may commit. Revoking recovery authority does not by itself invalidate grants already issued; review and cancel outstanding grants on incident. Command rotation leaves PIN hashes intact. PIN pepper rotation itself still requires separately reviewed migration or PIN recovery. Production key provisioning, automated rotation, audit/incident handling and managed secret custody remain unverified.

## Synthetic provider funding and reconciliation
Apply securepay-provider-sandbox-draft.sql after key rotation. The signed customer reservation now requires exact funded amount and no hold, checked under the milestone and funding locks. A dedicated provider runtime and independently provisioned provider key record signed synthetic events: funded, held, released and failed. The provider runtime has no direct access to PINs, grants or protected tables. Dispatch is a recorded synthetic submission; only a matching signed receipt with unique transaction reference can mark the submitted request confirmed and milestone released. Repeated identical event IDs do not reapply mutations; conflicting IDs and mismatched amounts/scope fail closed. A hold before submission blocks it; a hold after submission opens a reconciliation case, and a confirmed failure freezes the reservation. A sandbox receipt is never evidence of real funds or movement. No real provider, commercial webhook verification, automated retry, live refunds, live dispute settlement or reconciliation-resolution workflow is enabled. Legacy administrator integration fixtures deliberately exercise pre-provider transaction paths and are not API entrypoints.

## Independent dispute and settlement boundary
Apply securepay-dispute-settlement-draft.sql after the synthetic provider draft. Provision a verified customer, mapped business owner, independent reviewers and a separate settlement authorizer per tenant. Signed case actions open a dispute against an eligible funded milestone before dispatch, cancel pending ordinary requests, and block ordinary release by moving the milestone to disputed. Digests identify evidence, not independently verified evidence contents. A reasoned provisional decision needs evidence from both parties and exact cent conservation. Finalisation requires a different reviewer and either both parties acknowledging the provisional decision or both supplying appeal evidence; silence never authorises payment. The independent settlement authorizer must approve the exact final payout and refund. Only the provider role may record dispatch and a signed aggregate confirmation; the receipt is unique across ordinary and disputed payments. Provider-held funding cannot be overridden. All records are synthetic, with no money movement, and no ordinary customer PIN required for a separately adjudicated outcome. Production identity verification, conflict-of-interest checks beyond distinct account IDs, production rectification operation, verified evidence retention, statutory review rights, post-dispatch dispute reconciliation and live refund/payout leg execution, unresolved conflict handling and provider contracts remain unimplemented. Actor keys and roles are administrator-provisioned fixtures; no public dispute endpoints are enabled.

## Rectification and evidence
Apply securepay-rectification-draft.sql after the dispute settlement draft. Owner response deadlines are 2 business days for minor, 3 for moderate and 1 for serious cases. The sandbox counts Melbourne weekdays to 17:00, excluding administrator-provisioned holidays. Minor/moderate owner proposals require explicit customer agreement; serious cases require an independent reviewer plan. Deadlines must be documented and within 90 days, and only one repair cycle is implemented. Owner must provide fresh photo bytes after the repair start; the customer must acknowledge the same photo to accept repaired work. An accepted repair permits a full-payment provisional outcome only, never automatic payment. Late responses, repair deadlines or customer review deadlines create escalation records, not transfers. The restricted escalation scanner uses bounded batches and concurrent row locking; actual scheduling and delivery are not configured. The sandbox stores SHA-256-bound PNG/JPEG bytes (2 MiB/file, 12 per case), rejects mismatched image headers and duplicate evidence, and restricts reads to case parties or explicitly assigned reviewers. Photo header checking is not complete image validation, malware scanning or metadata removal. No external immutable evidence storage, production key custody, retention/deletion policy, verified holiday calendar, or public upload endpoints are configured. Existing allegations and general evidence are still digest references; the new post-repair photo path persists bytes.

## Evidence encryption and audit-chain verification
Apply securepay-evidence-encryption-draft.sql and then securepay-audit-chain-draft.sql after rectification. Both migrations refuse existing activity that would require a separately reviewed baseline or plaintext migration. Provision one independent 32-byte evidence key as write-enabled. Photo bytes are encrypted using PostgreSQL pgcrypto AES-256 OpenPGP with integrity protection; the original plaintext size and SHA-256 digest are checked on read. Retire the old write key and enable a new write key atomically; keep old read keys accessible for retained evidence. Missing keys and corrupted ciphertext fail closed. Keys remain inside the protected database, so this does not protect backups containing both keys and data or defend against a privileged database compromise. Real image decoding, antivirus, metadata removal, separate managed key custody, retention and key-destruction policies remain release gates.

The tenant-specific hash chain records transactional financial, credential-audit, dispute, evidence, deadline and notification changes plus successful photo reads. It stores hashes and minimal metadata, not raw PIN material, photo bytes or narratives. The audit runtime has read-only paginated export and checkpoint functions; a separate Node verifier checks sequence continuity and hashes against the current head and an optional previously retained checkpoint. Keep checkpoints outside the database under independently controlled immutable retention. Without this, privileged administrators can rewrite the entire chain and head; the chain is tamper-evident, not tamper-proof. Arbitrary denied operations, key administration, source-to-chain reconciliation, external checkpoint storage and audit export operations remain outstanding. No live financial processing is enabled.

## Evidence screening and retention
Apply securepay-evidence-screening-retention-draft.sql after the audit-chain draft. Evidence uploads require an independent, short-lived scan attestation bound to the exact digest, participant, case and photo ID. The old unscreened store function is revoked from the dispute runtime. The sandbox accepts only a strict, metadata-free 8-bit non-interlaced RGB/RGBA PNG subset, with bounded pixel count, compressed bytes, decoded bytes, CRC checks, filter validation and no trailing data. The subsequent normalized-evidence draft adds an opt-in bounded JPEG decoder and signed original-versus-stored provenance. The ClamAV adapter invokes a configured local executable without a shell and fails closed on infection, scanner errors or timeout. Database CI uses synthetic scanner verdicts. A separate evidence-engines CI job installs real Pillow and ClamAV and tests a deterministic local harmless signature; this does not establish production malware detection with maintained vendor signatures. Separate scan-key custody, deployment isolation and live scanner testing remain mandatory.

Evidence deletion requires an explicit administrator-approved retention policy, a settled case, elapsed retention date and no legal hold. No default destruction duration or automatic schedule is assumed. The restricted retention worker removes ciphertext from active records and preserves digest, timestamps and audit history; the tombstone cannot be retrieved as a photo. This is logical removal, not verified erasure from WAL, backups, filesystem remnants or prior exports. Review applicable Australian privacy, statutory record-retention and legal-hold obligations before enabling deletion. No live records have been purged.

## Normalized evidence and distributed abuse budgets
Apply securepay-normalized-evidence-draft.sql and securepay-shared-rate-limit-draft.sql after screening/retention. JPEG uploads require an explicitly provisioned Pillow decoder, bounded to 2 MiB compressed input/output, maximum 4 million pixels, 4096 pixels per dimension and an 8-second default subprocess deadline. The original upload and the metadata-free PNG derivative are both scanned; the signed attestation binds both SHA-256 digests and the original media type to the participant and photo. Only the PNG derivative is retained; the original hash is not a substitute for original forensic bytes, so original-preservation requirements must be separately reviewed. Existing evidence requires reviewed migration. The decoder is not a complete sandbox against native library exploits; OS isolation and patched dependency validation remain necessary. Large/incompatible images fail closed. The real-engine CI job uses distribution packages and a synthetic local ClamAV signature, not a maintained production threat database.

Every enabled standalone authority requires SECUREPAY_RATE_LIMIT_KEY (independent 32-byte hex key, identical across instances). The post-JWT shared budget records only keyed issuer/subject digests; it allows up to 20 authenticated operations per account and 600 total in a fixed UTC minute across authority instances sharing the same database. The global row serializes admission and bounds bucket cardinality; expired buckets clear on the next window. Database errors fail closed with 503; exhausted budgets return 429. Local pre-authentication limits remain, so distributed unauthenticated abuse, proxy and network flood protection, cross-region scaling and load testing remain production gates. Fixed-window limits permit bursts at minute boundaries and may need tuning. No external infrastructure or paid service configured.

## Individual settlement legs
Apply securepay-settlement-legs-draft.sql after the shared budget draft. Historical settlements require a reviewed migration. The old aggregate dispatch/confirmation functions are revoked from the provider runtime. A final authorized split creates one immutable nonzero payout leg and/or refund leg. Each leg has a stable identifier used as the external idempotency key, exact amount and bounded attempt counter. A signed provider outcome records confirmation, uncertainty or definitive non-execution. Unknown or non-executed outcomes block new dispatches; only a separate authorized settlement actor can enable a retry after confirmed non-execution, never uncertainty, and at most three attempts total. The provider must actually honor the stable idempotency key and independently establish definitive non-execution in any future live integration. Confirmation of one leg never repeats that leg or marks the settlement complete before every nonzero leg is confirmed. All successful receipt identifiers are globally unique across ordinary releases and settlement legs. Contradictory signed receipts are quarantined, logged and freeze remaining dispatch; unresolved conflicts block evidence purge. Late funding holds preserve prior signed confirmations, block new dispatch and record a reconciliation issue. No automatic reversal, case closure after a hold, conflict adjudication or recovery of exhausted retries is implemented. All events and receipts are synthetic; no real provider or transfers are enabled.

## Release blockers
- The 500-run qualification covers the original 52-test snapshot at commit 86b38751f79c4eabe58ecb94011e653ab2f2a313, not subsequent hardening. Requalify the updated test inventory before release.
- Payer invitation/provisioning and a real identity provider's purpose-bound step-up token issuance remain unimplemented. The sandbox verifies and consumes such assertions, uses an independent recovery signing key, and persists a replay ledger. The recovery key and verifier share the standalone authority process; further internal recovery-role isolation and external identity-provider session revocation remain required.
- The restricted payer runtime cannot directly mutate PINs, grant consumption, proof records, release requests or milestone states after applying the command-boundary draft. The narrow database functions recheck payer, state, version, amount, credential and scope; release and PIN change require exact, short-lived HMAC commands. Provision an independent command key into securepay_private.command_key via a trusted administrator, never the PIN pepper. Legacy derivation is retained for isolated test fixtures only. The service remains trusted to verify the PIN; full service or command-key compromise is not covered. A runtime with a valid signed payer context can still increment failure counters (denial of service within that payer's scope). The standalone sandbox authority separates these keys from the staff gateway; separately provisioned OS/container isolation, production key lifecycle operations and deployment review remain outstanding.
- Audit events for grant issuance/consumption, PIN changes/failures and release reservation are transactional and protected from the payer runtime. External immutable retention, independently retained checkpoints, source-to-chain reconciliation, full denied-request telemetry, notification delivery and external identity-provider session revocation, key rotation and distributed rate limits remain outstanding.
- Synthetic funding, hold, dispatch and receipt reconciliation are implemented; integrate a licensed provider under its actual contract, verify real webhook signatures and reconciliation, validate dispute authority, evidence, rectification and real settlement workflows, and review safe retries/settlements before live processing.
- Validate Australian legal and provider requirements independently. No claim of production readiness.
