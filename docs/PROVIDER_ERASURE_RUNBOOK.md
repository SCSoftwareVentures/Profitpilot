# Provider identity erasure (pre-production)
No production provider is connected. Do not run the destructive adapter on a real account until the provider integration, issuer provenance, MFA, legal retention and authorized synthetic end-to-end deletion tests are complete.

1. Verify the closed local user's subject belongs to the exact configured provider project. The existing local users table does not independently prove historical issuer provenance. Verify the user's request and separate approver, document references, and obtain authorized approval for this scope from every historic organization. Confirm no legal hold or open request and enable the explicit provider erasure policy only after legal review.
2. An authorized database operator issues a short-lived grant via private.authorize_provider_erasure(user_id, issuer, provider_subject, consent_reference, independent_approval_reference). References are evidence pointers, not proof of independent approval by themselves. Never store identity documents or secrets in these fields. No app role is permitted.
3. On an approved operator host, use a verified TLS database connection and secured provider credential scoped to the matching project. Set AUTH_ISSUER, PRIVACY_ADMIN_DATABASE_URL, SUPABASE_SERVICE_ROLE_KEY and PRIVACY_PROVIDER_ERASURE_ENABLED=true. Verify actual key/API compatibility first. Execute node scripts/supabase-provider-erasure.js <grant-uuid> only under the approved change. The adapter requires an exact Supabase project host; it disables redirects and rejects any identity mismatch before deletion. It confirms the provider's explicit user-not-found response, not merely a successful deletion response.
4. A timeout or uncertain outcome is not success. Keep local account disabled, investigate provider absence and obtain new authorization if needed. Local audit records and provider absence receipts are not evidence of physical data destruction. Update independent restore checkpoint and review backup/processor retention. Never reauthorize a different identity as a retry.
5. Provider refresh-token behavior, storage ownership, authentication logs, backups and downstream processors require separate verified handling. No automatic external deletion or blanket erasure is enabled.

Migration 023 supersedes the missing issuer-provenance limitation in step 1: login and erasure now require an explicitly provisioned immutable issuer/subject binding. Do not bind existing users without confirming historical provider provenance. Old outstanding grants and existing access sessions are invalidated on migration. Provisioning operators must set auth_issuer when creating users; unbound users cannot log in. No mapping or migration may be activated on a live database without reviewed recovery and cutover.
