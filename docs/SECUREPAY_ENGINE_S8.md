# SecurePay S8 — independently configured JWT issuer boundary

S8 accepts only short-lived RS256/ES256 JWTs verified against a separately configured issuer and remote JWKS. It enforces exact 15-field claims: issuer, audience, opaque subject/JTI, issued/not-before/expiry timestamps, tenant ID, case ID, evidence ID, signed claim ID, case job reference, claimed customer/tradesperson role, Ed25519 signing key digest, and the sole permission `synthetic_job_claim_review_only`. Maximum token lifetime is 10 minutes. Other fields (including personal information) are rejected.

The issuer is **not configured** by this work. An administrator must independently vet the provider, set `SECUREPAY_AUTHORITY_ISSUER`, `SECUREPAY_AUTHORITY_AUDIENCE`, `SECUREPAY_AUTHORITY_JWKS_URL`. Unsafe/non-HTTPS endpoints are rejected outside local tests, and reuse of the regular application identity issuer/JWKS is prohibited. Missing settings fail closed (HTTP 503). No third-party account is connected.

POST/GET: `/v1/tenants/:tenantId/prototype/securepay-cases/:caseId/evidence/:evidenceId/signed-party-claims/:claimId/issuer-attestations`. POST takes exactly `clientRequestId` (UUID) and `attestationJwt` (max 4 KB). The source scope comes from tenant RLS, not caller-supplied job details. A revoked underlying S7 claim blocks insertion in both the API and runtime-role database policy. Nonreusable issuer/JTI and request UUID constraints prevent duplicate token use. Raw JWT and real subject string are **not persisted**, only their SHA-256 hashes and bounded verification metadata. Responses to initial POST identify `issuerSignatureVerifiedAtRequest=true`. Replays and GET explicitly do **not** reverify the original JWT; expiry and revocation are reported on GET, with `usableForJobAuthorization=false` permanently.

This is cryptographic validation, **not verified customer/tradesperson identity or job authority**. Without an independent job registry, real-world credential issuance contract, revocable job memberships and verified original evidence bytes, a signed token does not justify dispute adjudication or payment settlement. Database CHECK constraints permanently keep these authorities false. Prototype routes remain disabled in protected deployments. Next: independent provider agreement, direct-party consent/credential lifecycle and verified evidence byte custody.
