# SecurePay SP-S9 — scanned synthetic evidence custody

This stage introduces bounded original-byte custody for **synthetic** evidence. A file POST uses `application/octet-stream`, with `x-client-request-id` (UUID), `x-evidence-sha256` (lowercase SHA-256) and `x-evidence-media-type` (text/plain, application/pdf, image/png, image/jpeg). Maximum size: 512 KiB. Claimed media types receive shallow signature/UTF-8 checks, not full file sanitation or semantic validation. Compressed uploads are rejected.

The **existing local scanner** is mandatory even in the prototype profile. A missing, unavailable or inconclusive scanner produces HTTP 503 without storage; infected yields 422. Successful scan status is `scanner_reported_clean`, not proof of immunity. The exact bounded bytes are passed to the scanner. No shell or arbitrary path is used.

POST and metadata-only GET: `/v1/tenants/:tenantId/prototype/securepay-cases/:caseId/evidence/:evidenceId/custody-file`. Requires active tenant owner/admin/reviewer; only a synthetic case with `funds_moved=false` may accept evidence. Append-only PostgreSQL custody table stores the exact received `bytea`, validates byte length and recomputes SHA-256 server-side, checks composite tenant/case/evidence foreign key and enforces forced tenant RLS and actor binding. An exact idempotent replay gets 200; attempting to replace any sealed evidence returns 409. No original-byte API download exists. The PostgreSQL runtime role cannot SELECT `original_bytes`.

**Limits and risks:** This only proves the server's received bytes match a declared hash at capture. It does NOT verify who originally created, signed or supplied the document, independent custody, or real customer-to-job authority. Bytes in PostgreSQL are not application-layer encrypted and have no independent external timestamp, secure deletion/legal hold process, retention schedule, production key management or verified restore privacy classification. Raw bytes may contain personal information: do not use real evidence in this synthetic-only environment. The app's HTTP scanner guard does not cryptographically bind a real scan verdict to DB writes: a compromised runtime database account could falsely claim clean scanning. No iPhone-specific upload testing or multi-megabyte file support exists. Protected deployment continues to reject synthetic routes.

The next major engineering work is separately anchored scanner attestations, protected encrypted object storage, consent and retention controls, and genuine issuer-backed party/job identity with revocation. Evidence receipts do not authorize adjudication or payment.
