# Production security release gate

Production startup fails closed unless both independent Ed25519 approval signatures authenticate an exact, time-limited release evidence document. No production defaults or synthetic approvals exist. The image must be built with an explicitly reviewed build revision (PROFITPILOT_BUILD_REVISION build argument); the running image reads its embedded revision. The release document must match that revision, the separately configured deployment identity and a hash of the non-secret security configuration. Evidence is required for every control enumerated by requiredReleaseControls in server/release-approval.js. A missing, failed, pending, expired or altered control prevents startup; approval expiry makes the API and health readiness unavailable.

## Operator procedure

1. Review the actual release artifact and record its immutable registry digest independently. Record current infrastructure, identity, TLS, encryption, key recovery, private file boundary, tenant/object tests, dependency/secret/container scan, backup recovery, incident exercise, privacy retention/processor review, penetration retest and risk-acceptance reports. Do not invent evidence or set verified merely because a development CI run passed.
2. Construct a JSON payload with exactly version (1), buildRevision, deploymentId, configurationDigest, issuedAt and expiresAt (UTC ISO timestamps, expiry within 30 days), and controls. Each required control maps to exactly {status:"verified",evidenceSha256:"<actual SHA-256 of reviewed evidence>"}. Obtain configurationDigest using releaseConfigDigest with the approved non-secret configuration. Neither credentials nor personal source records belong in this manifest.
3. Separate technical and privacy approvers independently review the evidence. Each uses an independently protected Ed25519 approval key on an authorised operator system. Run scripts/sign-release-evidence.js with the role, exact payload file, private key file and output signature file. The two public keys use base64url-encoded DER SPKI. The signatures are domain-separated by role; neither one can substitute for the other. Never transfer private approval keys into the API or public repository.
4. Construct the JSON document containing exactly payload (the original JSON text, preserved byte-for-byte), technicalSignature and privacySignature (base64url strings without newlines). Mount it read-only at the configured absolute path. Configure the separate public trust anchors using approved infrastructure configuration. Test startup with correct and deliberately invalid evidence, then verify health and actual provider interoperability.
5. Reassess or revoke approval immediately when release/configuration changes or a material incident occurs. Remove approval and drain/stop the environment for emergency revocation; a running process also refuses requests after the signed expiry. Run a reviewed deployment promotion, not an automatic merge to production.

This gate verifies cryptographic integrity, scope and expiry of operator attestations. It cannot determine if an evidence report is truthful, verify a human's qualifications, enforce separation of control over compromised host configuration or attest the image's external build provenance. Hosting, separate operator identities/keys, legal decisions, real evidence and independent assessment are still unconfigured. There is no live release approval or production deployment.

Development CI includes full-history and working-tree secret detection with Gitleaks, pinned CodeQL security-extended queries and Trivy production-image scanning in separate restricted-token jobs. A failed or unavailable scan blocks approval. Do not waive a finding or purge history merely to make the gate green; investigate, rotate genuine exposed credentials with explicit authority, remediate, and retest. No production approval follows automatically from scanner success.
