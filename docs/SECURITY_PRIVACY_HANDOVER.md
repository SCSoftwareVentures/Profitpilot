# ProfitPilot security and privacy handover — S3

Internal engineering and buyer due diligence. Not legal advice, independent certification, production approval or proof of actual deployed safeguards. Prototype is synthetic only. Never place customer data, actual privacy cases or credentials in the public repository.

## Deployment prerequisites
- Approved identity provider and HTTPS edge. Choose a provider-defined assurance value for AUTH_MFA_ACR and confirm its semantics; API checks verified acr and auth_time. Step-up freshness is 15 minutes for writes and 12 hours for reads. Verify real enrolment, revoked sessions, recovery, identity token issuance and expected claims.
- PROFITPILOT_PROFILE=protected requires DATABASE_SSL=true, separately mounted DATABASE_URL_FILE and TENANT_CONTEXT_HMAC_SECRET_FILE, MFA assurance, MALWARE_SCAN_MODE=clamav and an executable ClamAV scanner. Reject database URL TLS overrides. Mount trusted certificate material where needed. Require managed storage/database encryption, access-controlled secrets, rotation, revocation, backups, and tested custody/recovery. Actual HTTPS edge and encrypted volumes remain environment responsibilities.
- Optional Docker target protected installs ClamAV; mount signature definitions from a maintained approved source read-only at /var/lib/clamav. Confirm signature freshness, scan limits, permissions, process isolation, monitoring, update plan and real-file detection effectiveness. An unavailable or infected verdict refuses upload; exact source bytes are scanned. Existing unscanned receipts cannot be labelled clean. The CI native scanner fixture uses a harmless custom signature; this is not a real-world malware detection benchmark.
- Encrypted CI backup is a synthetic rehearsal using ephemeral GPG AES256 secret, with wrong-key rejection and restored row/source digest/RLS checks. No production backups or key escrow are established. Define per-environment backup schedules, recovery objectives, offsite retention, access controls, periodic review and disaster exercise. Keep recovery keys separate from encrypted backups.

## Privacy workflow and fulfilment
The API tracks verified active members' access, correction, erasure and restriction self-requests. Only the requesting member and active owner/admin see case metadata. Independent owner/admin review transitions requested -> reviewing -> closed_attested or declined, with opaque case reference. Audit review transitions; closure is external attestation, not evidence that the system independently verified fulfilment. No automated export or destructive deletion. Non-members and former staff need a staffed verified intake channel. Before live use document a data inventory: identity records, source uploads, raw rows, allocations, invoices, reports, audit, cases, support and backups; identify data owner, purpose, authority, retention, location, recipients, legal holds and approved disposal method. Privacy officer verifies identity, lawful authority and scope; searches approved stores/processors; reviews exceptions/holds; securely provides access or executes authorised correction/disposal; reconciles evidentiary dependencies and backups; retains minimum outcome evidence. No blanket deletion of financial evidence or unsupported retention periods. Verify data-subject fulfilment against representative records and documented policy before production.

## S4 scoped access and disposal
The self-access endpoint returns the authenticated member's stored identity, current tenant membership and up to 200 of their own privacy cases as a non-cached JSON attachment; flags overflow. It does not claim a complete data-subject export. Migration 016 defaults every import to retention hold. A privileged database operator, not the API/runtime role, can dispose of a narrow unused client-declared import only when an erasure case is independently reviewed by an active tenant admin/owner, requester created the batch, status is uploaded, hold is explicitly released under the same approved opaque policy reference, and no receipt, mapping, invoice lineage, payroll pool or recorded batch audit exists. Foreign keys remain final protection. Deletion, row-count verification and minimal audit are atomic; replay is rejected. The case remains in review for other stores, backups and actual legal fulfilment. No automatic retention duration, deletion of reviewed/verified evidence or physical-media sanitisation is claimed. Operator must assess legal holds, reference inventory, prior backups and approved scope before releasing retention hold. Test only synthetic data.

## S4 automated analysis
The configured full CI runs CodeQL security-extended JavaScript analysis and retains SARIF results; completion is not evidence of zero findings, and findings require review. Grype scans both prototype and protected images, retains all severity reports and blocks all reported critical and fixable high findings. Unfixed high findings remain visible for explicit risk review. This threshold is an engineering gate, not a certification. Provenance requires completion of analysis and container gates. No findings suppressed. Scanner database availability and current advisory coverage affect results.

Scanner version is pinned to a release SHA-256 obtained from its GitHub release asset metadata. Container scanning runs separately from the synthetic database job; generated CI database credentials are masked. Trivy installation failed in CI #2978 and was replaced without reducing the severity gate.

### S6 trial rejected; narrower Alpine remediation
CI #2981 confirmed the Debian experiment removed BusyBox but reported 9 critical and 265 high findings across images (all critical in protected image), versus zero high/critical in CI #2980. Reject the Debian trial. The protected Alpine/ClamAV image restores the previous hardened runtime with real APK inventory and no global npm/yarn/corepack. Alpine's scanner package depends on freshclam and the shell, so BusyBox may remain until a vendor update or a fully validated alternative. Prototype uses a from-scratch final image assembled from a signed minimal APK dependency set, no BusyBox or shell, with its genuine installed database and OS release metadata retained. No suppression or artificial package inventory editing. Both profiles undergo actual integration/scanner tests and Grype scans. CodeQL SARIF #2980 also contained three potential HTTP type-confusion findings and one file-system race. Explicit Buffer instance guards and byteLength handling plus descriptor-bound bounded secret reads address these findings; new CodeQL output must establish whether alerts clear. No claim of zero static findings until verified.
